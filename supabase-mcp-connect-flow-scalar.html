Supabase MCP client connect flow

How to build an OAuth client for the hosted Supabase MCP server — for partners embedding Supabase as a native connection inside their own AI builder platform, worked end to end with the Claude Agent SDK.

Last verified Sept 2026
The short version

Most of the integration effort here is OAuth, not MCP. Once you have an access token, connecting it to an MCP tool-calling loop is a few lines. Getting that token — and handling how Supabase's OAuth server behaves in practice — is the rest of this guide.

Discovery + registrationdiscovered at runtime, not a fixed pathPer RFC 9728 / RFC 8414

Scoping query params (project_ref, read_only, features) live on the resource URL, not as OAuth scopes. Whatever you append to the MCP URL is reflected into the discovery call and into the resource parameter sent to the authorize and token endpoints.

Not every client can do DCR

Supabase's docs note this directly: "If your MCP client requires an OAuth client ID and secret (e.g. Azure API Center), you can manually create an OAuth app." If your platform can't perform dynamic registration, create one from your org's dashboard instead and use its fixed client_id/client_secret in place of step 3 below.

2 Prerequisites

terminal bash

The Claude Agent SDK does not perform the OAuth flow for you. It only accepts a bearer token via headers on an http-type MCP server config. You run discovery → PKCE → DCR → authorize → token exchange yourself, then hand the SDK the finished access token.

5 Token refresh handling

Three distinct failure modes, three different fixes — don't lump them into one retry-and-hope handler.

Basic mechanics

Standard grant_type=refresh_token. Access tokens run roughly 1 hour. Your DCR registration must include refresh_token in grant_types or one won't be issued.

refresh.tstypescript

Failure mode 1 — improper storage of rotated refresh tokens

Every refresh issues a new refresh token; the one you sent is spent. This has already caused at least one real client failure — not a Supabase bug, a client-side storage bug.

Design implication

Persist the new refresh_token atomically with the new access token, before any other request. If two processes can refresh concurrently, serialize with a lock — the loser of a race gets stranded with a dead token.

Failure mode 2 — the client_id reaping mechanism

This is the "Unrecognized client_id" bug, now root-caused:

  • A 15-minute cron deletes DCR registrations that were never approved — abandoned mid-consent, or the user never finished the browser flow.
  • Revoking a connection deletes the row that shields an approved client from that same reaper. A client that registers, consents, mints a token, and is revoked within roughly an hour can fall back into the reap window.
  • A fully approved, actively-refreshed connection is not at ongoing risk — the danger window is abandoned or revoked-then-idle registrations, not steady-state usage.
Design implication

A spec-compliant error response looks like {"error": "invalid_client"}, which well-behaved OAuth clients already know to auto-clear and re-register on. Supabase currently returns {"message": "Unrecognized client_id"} instead — no error field — so that built-in recovery never fires. Keep the defensive STALE_CLIENT_ID string-matching above rather than relying on a generic RFC-6749-compliant handler alone.

Manual recovery for testing

claude mcp logout supabase then claude mcp login supabase. login alone is not enough — it preserves the existing registration when the redirect URI/port haven't changed, which just reproduces the failure.

6 Testing checklist

What to verify when running the full script above end to end.

  1. 1Discovery resolves both metadata documents without manual URL guessing.
  2. 2The consent screen appears and only succeeds for an org owner/admin.
  3. 3Token exchange succeeds and a Supabase MCP tool call round-trips end to end.
  4. 4Manually mangle the saved client credentials file and confirm the script detects the stale-client_id error and re-registers.
  5. 5If tool calls fail unexpectedly, rule out the SDK's HTTP transport version before assuming this auth code is wrong.
  6. 6Call the refresh function explicitly and confirm the new refresh token is persisted, not the old one.
